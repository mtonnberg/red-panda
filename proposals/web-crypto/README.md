Frozen independent Web Crypto and DOMException handoff

For a standalone integration, apply `dom-exception.patch`, `worker-dom-exception-bootstrap.patch`, then `web-crypto.patch`. When integrating the frozen Event/Abort foundation from codec_recovery, use its earlier DOMException install immediately after VM context creation and skip the separate bootstrap-only patch. The Crypto worker change is only its import and install after ImageData; rebase the import hunk if the foundation changes header ordering. The first patch is independent of Crypto; the second installs the helper before worker messaging/error capture. The third preserves the current Root CookieStore, media, URLPattern, Selection, Scheduler, Canvas and Storage integrations through narrow additions. All three patches were applied sequentially to an isolated copy of the current Root files, and exact new-file hashes match `frozen-manifest.json`. No Root files were edited. No new dependency or native-addon source change is required; use fresh processes for the new modules.

The helper source remains SHA256 `02dff903451159c4dee70ac10cae2163ca6d5b5dea4e48069cb36bc761b655a3`. It allocates actual VM Error values using the selected VM Error intrinsic and actual VM newTarget, keeps genuine Node DOMException backend values only in a private Host WeakMap, and exposes realm-local getters/stringifier/constants through strong successful-construction brands. It does not graft Host prototypes and does not claim that the public wrapper passes Node's private DOMException getter brand. The real backend does pass that brand. The direct Node-construction/newTarget attempt returned a Host Error and is retained as a counterexample in every genuine worker heap proof.

Crypto uses real Node cryptography for every digest, cipher, signature, derivation, import, export and key generation. Genuine private Node CryptoKeys back fresh selected-VM public wrappers; cached mutable algorithm/usages objects never authorize operations. Opaque real keys clone across actual workers and channels without exporting non-extractable key bytes. No captured-result lookup, target-engine import, fabricated key or fabricated cryptographic bytes are used.

Native-specific normalization includes ASCII algorithm matching, measured dictionary order and one-time name reads, delayed BufferSource byte snapshots, actual shared-buffer rejection, generation/PBKDF2 cost limits, strict DER boundaries, RSA integer/CRT and EC point/scalar checks, format aliases/error order, and canonical JWK member order. Canonical JWK wrapping uses a real temporary HMAC key containing the canonical UTF-8 bytes so Node's actual wrap implementation still enforces the wrapping key's usages and performs real cipher/CTR work. RSA-PSS verification checks the encoded-message invariant `saltLength <= ceil((modulusLength-1)/8)-hashLength-2` after genuine key authorization: an oversized salt cannot verify and returns false, matching Native even where Node24.19's WebCrypto adapter throws. Ordinary signature verification always uses the genuine backend; arbitrary backend failures are never converted to successful or failed verification results.

Window Crypto DOMExceptions use actual VM Error allocation followed by trusted generated Window DOMException setup with Host implementation slots. Already-converted messages bypass authored replacements of Window.String; the temporary captured constructor used during trusted initialization is removed before publication. Unrelated main-window DOMException construction is unchanged. Typed DOMException cloning reads private name/message slots and preserves graph aliases, ignoring authored extra properties, as measured in Native.
